# Pilot worker and Redis fault drill

Run `npm run test:pilot-evidence -- --faults` from the repository root with local Docker and installed npm dependencies. `PILOT_FAULT_COUNT` sets the number of synthetic original events per scenario (default 20, maximum 100,000); `PILOT_FAULT_DRAIN_SECONDS` sets the bounded recovery wait (default 90). This is separate from the volume, burst, backup, and restore drills.

The harness creates fresh local PostgreSQL and Redis containers, a unique queue, one API, and a worker. It runs a healthy baseline, a stopped worker, a worker process that exits just after claiming an event, Redis job loss via `FLUSHDB` while the worker is stopped, and Redis stop/restart. It sends only through `/api/track`. After each fault, it restarts the worker or Redis, waits for projection and rating, and replays the same deterministic keys and payloads. The 30-second PostgreSQL claim lease may determine the crash scenario's recovery time. The report records checkpoint backlog, row counts and quantities, queue counts, attempts, and recovery duration. Redis outage attempts can receive accepted IDs because the database commit precedes queue dispatch.

The report separates drain time after sending from fault-to-reconciliation time, and gives no finite recovery time on a timeout. Each scenario marks the volume, Customer count, burst, one-minute processing, and four-hour ingestion-restoration targets as pass, fail, or unmeasured. The default sample is too small to establish the volume targets; no production target is inferred from it. Queue drainage is recorded separately from database reconciliation.

Final reconciliation checks every raw event in the run Organization against the original sender journal, including IDs, quantities, Customers, metrics, UTC months, projection, rating, and price. It also compares grouped counts and quantities, fails on extra rows or unfinished database/queue work, and resolves uncertain HTTP responses with Organization-scoped idempotency lookup before replay. A lookup failure remains unresolved in the report. Worker stop is injected after a claimed event is observed. `PILOT_FAULT_ONLY=<scenario>` runs one scenario for local diagnosis. The Docker-backed regression checks are `node --test scripts/pilot-evidence-faults.test.mjs`.

The runner retains `fault-sender-journal.jsonl`, `fault-evidence.json`, API and worker logs, and process identities under `/tmp/usageflow-pilot-evidence/<run-id>` (or `PILOT_EVIDENCE_DIR`). It records the journal byte length and SHA-256. The journal contains synthetic payloads and response bodies, not the API key or database password. All five scenarios and failures remain in the report. The drill measures worker and queue recovery only; PostgreSQL restore RTO and RPO remain unmeasured. Keep the pilot gates closed.

On normal exit the runner removes its named containers and registered child processes. If interrupted, run `bash scripts/test-pilot-evidence.sh --cleanup <run-id>` with the same `PILOT_EVIDENCE_DIR`. Cleanup retains the evidence for review and checks process identity before sending signals.
On a failed run, the runner also writes a `runFailure` entry and the journal checksum to `fault-evidence.json` before removing run-owned services.
