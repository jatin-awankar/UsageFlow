# Pilot volume and burst drill

Run the small routine check with `npm run test:pilot-evidence -- --smoke`. The larger drills are separate and opt in:

```sh
npm run test:pilot-evidence -- --volume
npm run test:pilot-evidence -- --burst
```

`--volume` sends 100,000 distinct keys in one current UTC-month fixture, with 20,000 events for the primary active Customer and 80,000 for a second active Customer. Quantities cycle through 1, 2, and 3. Eight sender loops operate concurrently. `--burst` schedules ten original requests each second for ten seconds (override with `PILOT_BURST_SECONDS`). Up to four recovery passes resend missing original keys with their unchanged payload after a transport or HTTP failure. Both modes then send three identical retries and three changed-quantity conflicts. The report distinguishes original HTTP attempts, all attempts, observed accepted IDs, persisted unique rows, and achieved rates. Rate uses actual monotonic elapsed time, including delays from journaling and the API.

Each run starts fresh local PostgreSQL and Redis containers, one Next.js API process, and one worker. The pilot ingestion gate is set only on those child processes. Finalization stays disabled. No event or derived measurement row is inserted directly. The runner retains `sender-journal.jsonl`, `<mode>-evidence.json`, `api.log`, `worker.log`, and process identities under `/tmp/usageflow-pilot-evidence/<run-id>` (or `PILOT_EVIDENCE_DIR`). The journal is flushed before each send and after each outcome; the evidence includes its byte length and SHA-256. No API key or database password is saved there.

The runner removes only its named containers and registered child processes on exit. After an interrupted run, execute `bash scripts/test-pilot-evidence.sh --cleanup <run-id>` with the same `PILOT_EVIDENCE_DIR` setting. This retains the journal and report. Review them before removing their run directory.

The final report reconciles each deterministic key to an original ID, Customer, quantity, processing intent, and matching rating; it records receipt window, backlog at the end of sending, final missing outcomes, and independent projection and rating latency distributions. PostgreSQL computes both differences from persisted timestamps; `receivedAt` and `projectedAt` are timestamp columns without time zones and are interpreted as UTC, while `ratedAt` includes a time zone. Precision is milliseconds. A missing timestamp remains in the accepted-event denominator. The drain wait defaults to thirty minutes (`PILOT_DRAIN_SECONDS`), after which missing outcomes fail the run.

These are local capacity measurements only. Resource saturation is currently unmeasured, and container CPU and memory limits are unspecified. The drills do not establish production capacity or a recovery guarantee. Worker interruption, queue loss, restore, replay, and export checks belong to later tickets; their outcomes remain unmeasured here. Keep all pilot rollout gates closed.

## Local results on 2026-09-29

The host was an Apple M5 with 10 logical CPUs and 16 GiB RAM. Docker reported a 7.817 GiB available memory ceiling; neither PostgreSQL nor Redis had a per-container CPU or memory limit. Both used local loopback ports. One Next.js process and one worker with concurrency 5 ran against PostgreSQL 17.6 Alpine and Redis 7 Alpine. Docker samples are point-in-time measurements, not peaks. At the final volume report, PostgreSQL was using about 100% CPU and 225 MiB, Redis about 0.2% CPU and 24 MiB, and host free memory was about 84 MB. Host load averages were 4.86, 5.87, and 5.77. These observations cannot establish a production saturation margin.

The first volume run (`d925a964-cdc`) failed visibly: 99,998/100,000 distinct keys persisted from 100,006 HTTP attempts, including two HTTP 500 transaction-start timeouts. Its end-of-send checkpoint still lacked 22,668 projections and 22,671 ratings; the old drain guard skipped waiting when raw count was short. Its journal and failed report remain under `/tmp/usageflow-pilot-evidence/d925a964-cdc`. This prompted bounded same-key recovery sends and the corrected drain wait.

The final successful volume run (`3fa4be6c-d9a`) persisted 100,000 distinct events, including 20,000 for the primary Customer. Expected, raw, projected, and rated quantity, and rated amount, were each 199,999. It made 100,008 HTTP attempts: 100,003 HTTP 200, three expected HTTP 409 conflicts, and two HTTP 500 responses recovered using the same keys. All three explicit identical retries retained their original IDs. Ingestion took 1,530.359 seconds, for 65.344 distinct acceptances/second; the persisted receipt window was 1,530.166 seconds. At send end, 19,518 projections and 19,521 ratings were outstanding. All 100,000 eventually projected and rated; final pending, processing, failed, unrated, rating retry, and rating failure counts were zero. Projection latency from persisted `receivedAt` was p50 182.163 s, p95 287.049 s, p99 289.732 s, maximum 290.743 s, with 90,809 above 60 s. Rating latency was p50 182.224 s, p95 287.102 s, p99 289.784 s, maximum 290.789 s, with 90,820 above 60 s. Both stages finished within a minute for 9,180/100,000 (9.18%). The 100,000/month and 20,000/Customer count checks passed locally; the healthy one-minute processing target failed at this load. The preceding successful run (`f2ccfd29-df2`) also remains available and measured 49.271 distinct acceptances/second with 8.336% completing both stages within a minute.

The final burst run (`f7778e50-17a`) requested 10 requests/second for 10 seconds. It persisted 100 distinct events from 106 attempts: 103 HTTP 200 and three expected HTTP 409. Its achieved original and unique acceptance rate was 10.067/second over 9.933 seconds, with a 9.742-second persisted receipt window. Each of the ten one-second response buckets contained ten original acceptances. End-of-send and final projection/rating backlog were zero. Projection p50/p95/p99/max were 23/28/58/60 ms; rating values were 35/44/73/82 ms. No timestamp was missing and all 100 completed both stages within 60 seconds. This local 10/second burst target passed for the recorded duration.

The final reports and journals remain under `/tmp/usageflow-pilot-evidence/3fa4be6c-d9a` and `/tmp/usageflow-pilot-evidence/f7778e50-17a`. The final volume journal SHA-256 is `986184427904a2e6386a9487a1d67126c163e40c449f3aee1f0808a4bd8b3493`; each report records its own journal hash. Recovery RTO, backup RPO, export timing, and replay outcomes remain unmeasured in this ticket. No capacity or recovery guarantee is approved; pilot gates remain closed.
