# Recovery scan step 2: lock diagnosis and paired 20,000-event runs

The timeout in `tests/unrated-recovery.spec.ts:100` is a worker recovery defect exposed by the test's `ACCESS EXCLUSIVE` lock on `RatedEvent`. Step 1 reproduced the same `PENDING` timeout with both the original Prisma candidate query and the single-join query. This step reproduced it with the single-join query and captured a PostgreSQL lock snapshot: the unrated recovery `SELECT e.id ... NOT EXISTS (SELECT 1 FROM "RatedEvent" ...)` waited on a relation lock, while the blocker was idle in the lock-holding transaction. The worker used one `recoveryRunning` guard for ledger, rating, and webhook recovery. A blocked rating scan kept that guard true, so the next ledger scan never enqueued the deliberately lost dispatch. The original query was not the cause.

The follow-up gives ledger, rating, and webhook scans separate in-flight guards. It keeps the ledger candidate query and the crash/restart assertion intact. The unrated test now waits for the rating scan to be blocked before sending `unrated-interrupted`, then still requires the event to reach `PROCESSED`, kills the worker while its rating query waits, restarts it, and requires one rated row. Its 30-second polling limits were not increased. The suite passed with both query variants after the fix. An intermediate development run failed because the newly extracted rating function lacked its `queue` binding; that was corrected before the paired load runs and final checks.

The comparison used `PILOT_DIAGNOSTIC_EVENT_COUNT=20000 WORKER_CONCURRENCY=5 PILOT_DIAGNOSTIC_QUIET_WORKER=true npm run test:pilot-evidence -- --volume`, with separate `PILOT_EVIDENCE_DIR` roots. Each completed run used fresh loopback-only PostgreSQL 17.6 and Redis 7 containers, one production-mode API, eight sender loops, worker concurrency five, the same 20,000 deterministic events, the same journal, trace, database, queue, and Docker-stat samplers, and the same per-candidate-query wall timer. For the original variant only, `findRecoveryCandidates` was temporarily replaced with the Prisma filter from the parent of PR #99; all other worker code, including the recovery fix, was the same. The single-join function was restored afterward. Full reports, sender journals, and worker logs are under `/tmp/usageflow-step2-old/ba9192ea-50b/` and `/tmp/usageflow-step2-new/9461689c-e50/`.

Sender rates differed by 0.071/s (0.06%); these were achieved rates from an unpaced sender, not fixed offered load. The single-join scan was faster, but the paired end-to-end run did **not** show a throughput gain. Its terminal throughput was lower by 2.601/s, with deeper queueing and higher latency. Sequential runs experienced different host contention and cannot attribute the end-to-end difference to the candidate query. Terminal throughput divides the 20,000 final ratings by report start-to-end wall time, including sending and draining; it is not an instantaneous worker service rate. Scan wall times include Prisma/database round trips and only completed scans; they are not cumulative database CPU.

Both runs used an Apple M5 host with 10 logical CPUs and 16 GiB RAM. At report time, host load averages were 5.17/3.49/2.94 (original) and 4.32/4.25/3.42 (single join); reported free memory was 130 MB and 346 MB. Point-sampled PostgreSQL CPU was 101.18% and 100.30%, Redis CPU 0.49% and 0.25%. Docker reported no explicit CPU or memory limits. These are endpoint samples, not peaks.

Each completed run had 20,006 HTTP attempts: 20,000 accepted original keys resolving to 20,000 distinct persisted, projected, and rated IDs, three same-ID retries, three expected 409 conflicts, and zero unresolved transport attempts. Expected, raw, projected, and rated quantity and rated amount were all 39,999; the primary Customer held all 20,000 events. All 20,000 reached projection and rating within 60 seconds. Final pending, processing, failed, unrated, rating-retry, rating-failure, missing projection, missing rating, and queue backlog were zero; each report's failure list was empty. Independent `shasum -a 256` checks matched report journal values: original `05e923c2dbc7cbcb86772aca394afc2a44a684f540043589f7967fca06c2c4c5`, single join `dedc69d11584a79d45f4d4445fa997fc24e90f18b0422cf898b873999ba1e928`; both journals were 16,331,320 bytes.

One preliminary original-query run (`/tmp/usageflow-step2-old/772ce25c-b04/`) was intentionally interrupted before the measurement completed so the same per-scan timer could be added to both variants. It has no completed report and is excluded. The final original and single-join runs both completed with no recorded failures. `npx tsc --noEmit`, `scripts/test-ledger-worker-recovery.sh`, `scripts/test-recovery-candidate-query.sh`, and `scripts/test-unrated-recovery.sh` passed on the restored single-join code. The original-query unrated suite also passed with the fix. The 100,000-event run remains step 3; no pilot gate decision follows from these smaller runs.
