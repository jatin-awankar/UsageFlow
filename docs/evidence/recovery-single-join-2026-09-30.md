# Recovery candidate single-join diagnostic (2026-09-30)

The only production change replaces the recovery candidate selection query with one `UsageEvent` join. It retains `LEDGER_ONLY` eligibility, `PENDING` only after the one-second dispatch cutoff, `PROCESSING` and `FAILED`, null or expired leases, `(createdAt, eventId)` cursor order, wraparound on an empty cursor page, and the 200-row limit. The later pending-state recheck and unrated recovery query are unchanged.

A disposable PostgreSQL 17.6 test compared complete ordered candidate rows from the original Prisma filter and the new query. Fixtures covered old, exact-cutoff, and fresh pending intents; failed and processing states; null, expired, exact-expiry, and live leases; legacy and processed exclusions; 205 same-time candidates spanning the 200-row boundary; and three cursor positions. It passed. `npx tsc --noEmit` and the lost-dispatch worker suite passed, including queue loss, restart, interruption, duplicate execution, failed retry, and projection reconciliation.

The unrated recovery suite failed twice with the new query and once with the original query temporarily restored. All three runs timed out at `tests/unrated-recovery.spec.ts:100`, waiting 30 seconds for `unrated-interrupted` to become `PROCESSED` while the test held an `ACCESS EXCLUSIVE` lock on `RatedEvent`; it remained `PENDING`. The baseline run returned the same assertion and the single-join file was restored afterward. This is a reproducible suite failure, not a passing check or evidence that this query caused it. No test or worker behavior outside candidate selection was changed to mask it.

The paired `EXPLAIN (ANALYZE, BUFFERS)` statements in [recovery-paired-plan-2026-09-30.sql](recovery-paired-plan-2026-09-30.sql) ran in one read-only repeatable-read snapshot with 14,028 accepted and 11,792 rated events. The original three-join shape took 17.912 ms and 2,975 shared-buffer hits. The one-join shape took 5.951 ms and 1,159 hits, including one scan of `UsageEvent`; both returned the 200-row limit. The output is in [recovery-paired-plan-2026-09-30.txt](recovery-paired-plan-2026-09-30.txt). This is a warm-cache snapshot during load, not a guarantee of scan time under every state or cursor. In the first new-query load report, the latest candidate statement entry retained by the top-20 statement sampler showed 63 calls, 62.473 ms cumulative, 0.992 ms mean, and 2.845 ms maximum; it dropped below the top 20 later, so this is not a full-run cumulative measurement.

Two sequential production-mode diagnostics each sent 20,000 distinct events with eight sender loops, one API process, and worker concurrency five. For each run, all 20,000 original keys resolved to distinct accepted IDs, all IDs matched persisted rows, projections, and ratings, and expected, raw, projected, rated, and rated-amount totals were each 39,999. The primary Customer held all 20,000 events. All 20,000 completed both stages within 60 seconds in these smaller runs. Both had 20,006 HTTP attempts, three same-ID retries, three expected 409 conflicts, and no unresolved transport attempts.
