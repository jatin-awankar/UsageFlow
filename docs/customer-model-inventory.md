# Customer inventory and restored-copy reconciliation

The September 26 inventory was run against the **pre-Customer schema**. Its saved private baseline, independent organization and table counts, identifier partitions, and SELECT-only role check were verified then. `scripts/inventory-customer-model.ts` remains the historical-schema reader for that baseline. Its statement that no Customer table exists describes that old schema, not the current repository. Do not compare its output directly with a current-schema run as if both had the same columns or billing treatment.

The current schema has `Customer`, nullable `UsageEvent.billedCustomerId`, and `UsageEvent.billingTreatment`. The raw `UsageEvent.customerId` and `Subscription.externalCustomerId` remain legacy evidence. Missing, blank, User-ID-shaped, and arbitrary nonblank identifiers are **unmapped** until a separate, documented source-system decision proves attribution. A `LEGACY` event remains excluded from Customer billing even if it has a Customer link. Never derive a billed Customer from `Subscription.externalCustomerId`; subscription creation historically stored a `User.id` there.

## Current-schema run on a recent isolated production restore

1. Obtain a production-source custom-format archive captured within 48 hours, with an independent source/capture record and SHA-256. Record the archive header from `TZ=UTC pg_restore -l <archive>`, plus the isolated restore's creation log and database name. The archive header has no source host or trustworthy UTC consistency point, so an operator must verify source attribution and capture timing separately. Use a local loopback PostgreSQL restore with a name other than `postgres`; never point this command at a live database.
2. Before migration rehearsal, inspect `_prisma_migrations` on the isolated copy using a separate **restore-only** administrator. Compare names, completion state, and migration checksums with `prisma/migrations`. Retain a full isolated-copy backup and the initial migration state. Apply only reviewed additive repository migrations to that copy. If a migration fails, preserve the failed copy and logs; do not proceed to application rollback.
3. After the copy reaches the current schema, create a dedicated inventory role on the isolated copy. Grant only `CONNECT`, `USAGE` on `public`, and `SELECT` on the tables checked by the script, including `User` and `_prisma_migrations`. Revoke `TEMP` and database/schema `CREATE`; ensure the role has no superuser, create-role, create-db, replication, bypass-RLS, or inherited write rights. Set its default transaction mode to read only. Test a SELECT and rejection of INSERT and TEMP before using the role.
4. Put a private manifest outside the repository with `kind: "usageflow-isolated-production-restore"`, `isolated: true`, `restoreId`, `sourceEvidence`, `restoreEvidence`, `sourceCapturedAt` (ISO UTC), `archiveCreatedAt` (exact `TZ=UTC pg_restore -l` header), `backupPath`, `backupSha256`, `database`, and `readOnlyRole`. The source and restore evidence fields point to retained operator records; the command checks their presence, while an operator must validate their contents. Do not include passwords or connection URLs in the manifest. Compare the source time, archive header, checksum, restore log, and manifest before running.
5. Run `npm run test:inventory && npm run test:current-restore-reconciliation`. Then run `INVENTORY_DATABASE_URL='postgresql://READ_ONLY_USER:REDACTED@127.0.0.1:5432/usageflow_isolated_restore' npm run reconcile:current-restore -- /private/path/restore-manifest.json > /private/path/current-reconciliation.json`. Keep the URL and full report private. The command never reads `.env` or `DATABASE_URL`. It refuses non-loopback URLs, stale or mismatched archives, a database/role mismatch, write-capable role, missing/current-schema columns, unfinished/unexpected/checksum-mismatched migrations, and inconsistent count partitions.

The command opens one `REPEATABLE READ READ ONLY` transaction, checks the role and migration state, independently reconciles per-organization Customer, Subscription, UsageEvent, Invoice, BillingRecord, WebhookEvent, and replay counts, then rolls back. It reports hashed organization references, legacy identifier categories, billing treatment, legacy invoice totals, and global billing/webhook evidence counts. This is a snapshot of stored records, **not** a Customer mapping, invoice-money reconciliation against an external system, sender-ledger comparison, or proof that every billing/webhook row is byte-for-byte preserved. Keep ambiguous original rows and all historical billing evidence for explicit review.

For a migration or application rollback rehearsal, capture this report and a full evidence-table logical export/hash on the isolated copy before and after each step. Compare row IDs, monetary values, status, payload, target selection, work, attempts, replay, and request records, not only counts. Stop billing workers before rolling application code back; retain the additive schema and all committed versions and webhook events. Use a reviewed rollback application build, then restore the current build after the check. Never restore an older database over the rehearsal copy to claim application rollback passed. Record sender-side original event IDs and outcomes separately; recovered quantity does not prove original IDs survived.

The deployed Customer ingestion and owner finalization gates stay closed until a separate rollout decision reviews representative migration, rollback, restore/replay, receiver, and intended-host evidence.
